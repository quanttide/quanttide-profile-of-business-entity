# GitHub 活动面板项目

> 本档案是一个真实数据项目的复盘记录，记录定位、结构、质量与复盘。内容已脱敏，仅保留数据源与处理方向，隐去客户身份与核心字段口径。随迭代更新、反映当前理解，不追求一次写全。

## 定位：构建用户每日活动面板

一个真实的学术数据工程项目：基于公开的代码托管平台数据（如 GitHub 及其开源数据集），为学术研究构建一个按用户 × 日期排序的用户-日面板数据集，记录用户级的每日活动指标。

## 核心目标：新增指标并跑通可复现管道

1. **新增扩散类指标**：统计某日新建的项目在一年内/全生命周期获得的扩散数量（含活跃扩散，共 4 个指标）。
2. **新增合并拆分指标**：把某类合并行为拆成自合并 / 外部合并两类。
3. **可复现**：用 qtcloud-data CLI（clarify → design → spec → implement）把真实项目复现成可复现的数据管道。

## 数据结构：活动面板的通用处理模式

从真实项目抽象出的通用模式（具体字段名已隐去）：

**输入**：
- 目标用户清单
- 平台基础表（用户、项目、提交、合并请求等）
- 扩散关系由项目表的来源字段推导

**处理流程**：目标群体筛选 → 关系提取 → 指标计算 → 面板聚合

**输出**：用户 × 日期面板，含活动计数、扩散计数、合并拆分计数等指标

## 数据质量：从真实项目「用」出来的口径

- **内部一致性**：拆分指标之和应等于总量（逐用户 × 日期精确成立）
- **子集关系**：活跃扩散 ≤ 总扩散、一年窗口 ≤ 全生命周期，逐行成立
- **窗口边界**：时间窗口按 UTC 日历日，边界约定要明确（如左闭右开）
- **右删失**：数据有截止日期，需生成「窗口完整可观测」的指示变量
- **时区统一**：数据载入与查询统一时区，保证日期计算一致

## 复盘与开源（核心用途）

从复现过程中复盘出的经验教训：

- **口径管理**：变量定义必须以客户的数据字典为准，不能按自己理解设计
- **扩散来源**：扩散类指标要看样本外的扩散，不是样本内部互相关联
- **通道选择**：活跃判定要选对数据通道，避免继承关系带来的假阳性
- **CLI 工作流**：LLM 调用无进度、契约复用缺失、规格包装丢字段、review 假阳性等
