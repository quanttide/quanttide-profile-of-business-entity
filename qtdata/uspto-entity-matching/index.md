# USPTO 实体匹配项目

> 本档案是一个真实数据项目的复盘记录，记录定位、结构、质量与复盘。内容已脱敏，仅保留数据源与处理方向，隐去客户身份与核心字段口径。随迭代更新、反映当前理解，不追求一次写全。

## 定位：把公开专利数据中的实体名称匹配到金融数据库

一个真实的学术数据工程项目：把美国专利商标局（USPTO）公开专利/商标数据中的**实体名称**，模糊匹配到金融数据库中的**上市实体 ID**，建立专利数据与金融市场数据的关联桥梁。

## 核心目标：跑通匹配流程并复盘开源

1. **匹配**：把公开数据中的实体名称标准化后，模糊匹配到金融数据库 ID，产出带置信度的匹配结果表。
2. **复盘**：把「旧实现 → 用 qtcloud-data CLI 重新跑通」过程中踩的坑，复盘成可复用的经验。
3. **开源**：把字段口径、匹配算法、质量标准抽象成开源的数据工程资产。

## 数据结构：实体匹配的通用处理模式

从真实项目抽象出的通用模式（具体字段名已隐去）：

**输入**：
- 公开数据源（专利/商标类）：含实体名称、地址、地区等字段
- 映射表：含标准实体名

**处理流程**：名称标准化 → 模糊匹配 → 提取待审核 → 审核 → 合并导出

**匹配结果**：原始名称、标准化名称、匹配到的 ID、匹配类型（精确/高置信/低置信/无匹配）、置信度分数、数据来源

## 数据质量：从真实项目「用」出来的口径

- 标准化会去重，但同一实体名在源数据中出现多行是正常现象，不能当重复错误
- 匹配质量：精确匹配优先，模糊匹配回退；用索引加速大规模匹配
- 审核分级：自动通过 / 自动拒绝 / 人工审核

## 复盘与开源（核心用途）

从复现过程中复盘出的经验教训：

- **字段口径冲突**：真实数据字段名与生成脚本通用字段名不一致，需在规格里明确输入契约
- **算法选择**：实体匹配不能只用严格等值匹配，必须用模糊匹配 + 索引/去重，否则性能和召回都崩溃
- **性能**：禁止对海量行逐行模糊匹配，必须先按标准化名去重再匹配
- **AI 接口**：AI 审核接口要明确 OpenAI-compatible 配置，不能默认占位接口
